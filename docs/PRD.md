更新日期：2026-10-05（R11）。范围：既有体验与数据优化、顾问交接的局部改动、整体视觉改版、自建菜谱编辑/照片和默认分量，以及R8餐次/照片收尾、R9照片/完整删除、R10替换确认/双类别管理/待吃提示、R11现有食谱直接管理与已吃菜份。本文为当前需求入口；各轮交接用于追溯当时的实现与验证，不替代本文的当前状态。

## 1. 产品定位与边界

帮助用户方便地记录饮食、查看热量与营养摄入、安排饮食计划和维护自己的菜谱。优先保证记录方便、计算口径一致、数据可保留，再完善视觉与操作细节。

- 在现有项目上改进，不另做与实际程序脱节的模板。
- 技术栈经源码核对为 uni-app、Vue 3、TypeScript、Pinia 和本地存储，目标平台为微信小程序，H5用于预览及分层验证。
- 推荐为本地规则计算，不是大模型推荐；不默认增加账号、云同步、后端或图片识别。
- 用户确认优化开始时 GitHub 为最新源码；微信因重名申请过名称变更，旧 Markdown 未及时更新。当前名称统一为“一口一口瘦”。
- 2026-10-04用户确认本地效果“可以了”，授权将当前工作区提交、推送GitHub并更新Markdown；本轮不部署、微信提审或发布。微信开发者工具与真机尚未验收，线上版本与本版源码的对应关系未核验。

## 3. 关键操作与验收标准

### 3.1 记录、日期与计划

- 添加食材后选择实际克数，保存成功后刷新仍保留；修改克数应同步更新该条摄入及汇总。
- 删除记录前有反馈与确认路径；最近操作可撤销。撤销不能覆盖后续新操作，切日期或重开后不能依赖它恢复。
- 昨天和今天的记录、计划独立；历史页有明确提示，支持返回今天。已有历史目标保留；旧数据没有目标时显示缺失，不反推。
- “记已吃”仅记未吃成员，重复点击不重复计入；“全部待吃记已吃”处理当天全部待吃计划，文案与选择范围一致。
- “撤回已吃”扣回精确关联的记录并将计划恢复待吃；“移除计划”只去掉计划，已摄入保留；删除对应记录时，关联计划恢复待吃。
- 一份菜谱在计划中是一行及一个操作单位；两次添加同名菜谱仍是两份。部分已吃时只补记剩余成员。
- 旧数据无法可靠归组或无法确认记录关联时，提示需核对，不按名称猜删、归组或重记。
- 首页“记录饮食”进入今天已吃，首页/食谱的计划入口进入今天计划；从历史日期跳转也回到今天对应列表。加入成功反馈对应真实保存结果，并提供查看计划入口。
- 计划显示原计划热量，摄入显示实际记录热量；已吃每份菜显示一次菜名，下方紧凑列出逐配料明细。修改实际分量前展示当天合计变化，保存后可撤销，不追溯改原计划。

### 3.2 起始日与自建菜谱

- 首页天数为普通显示文字，只有“调整起始日”触发日期选择。选今天是第1天，选6天前是第7天，取消或保存失败保持原日期。
- 自建菜谱横向点击分类，内容区切换对应食材；可命名、添加、修改克数、移除和保存。修改已有菜谱时回填副本，保存更新原ID，不产生重复菜谱；取消不改原内容，未改草稿退出不询问，有未保存变化再确认。
- 自建可添加、更换、移除照片；卡片、详情、编辑区一致显示，缺图/加载失败使用默认图。选择或保存失败保留原照片/草稿，刷新后照片仍存在。
- 编辑只影响菜谱及之后的新加入，之前的计划、已吃快照与分量记忆保持原样，界面说明该边界；既有自建描述保留，自动配料计数描述随数量更新。
- 新选择油为5克/步进1克，坚果/籽类15克、酱料10克、牛油果50克、鸡蛋50克、燕麦40克、米饭150克、常见肉类100–150克、蔬菜通常150克。自定义油类及明确名称的坚果/酱料/牛油果使用小起点，其他自定义食材保留参考量；均可精确编辑，不迁移改写已有克数。
- 手机窄屏下内容不横向溢出，保存入口可达；真实键盘遮挡、滚动和安全区需在微信真机检查。

### 3.3 餐次、隐藏与照片清理（R8）

- 新建/编辑提供早餐、午餐、晚餐、加餐。具体餐次筛选进入时预填该餐次；全部/自建默认午餐，表单明确显示并允许修改，不凭名称猜测。编辑保留原餐次，旧数据不批量重写。
- 只有餐次变化也纳入未保存提醒；从具体筛选改为另一餐次并保存后，列表切换到新餐次，避免保存后找不到菜谱。卡片显示自建及餐次标签，刷新仍与筛选一致。
- 管理提供隐藏菜谱入口，兼容已有隐藏项、无照片项及预设菜谱；旧来源不在库中时只能移除隐藏标记，不凭空重建内容。隐藏只移出列表，照片仍计入512KiB配额。
- 移除照片前确认释放的实际编码占用与影响范围；只删除该菜谱可选photo字段，文字、配料、隐藏状态、历史计划/已吃与分量记忆保留。取消/写入失败保持原数据，过时确认不执行；撤销隐藏不会复活已清照片。旧备份或导入前副本可能仍含照片，清理不能直接撤销照片。
- 照片超限提供真实清理入口，在编辑面板上方打开，不丢名称、餐次、分量和照片草稿；释放后及时移除旧超限提示，仍由真实持久化成功决定是否关闭编辑。

### 3.4 计划照片和完整删除（R9）

- 新计划成员携带可选recipeId，图片读取当前源菜谱，不将整张照片重复存到每份计划/配料。自建照片可在首页待吃和计划显示，隐藏/改名/调整源菜谱分量不影响编号关联；实际克数编辑不追溯改变计划。图片属于当前源展示，不是历史照片快照。
- 旧计划无编号时只用完整名称与配料/克数的唯一匹配，不为不可靠旧分组猜图。有明确编号但来源已删除，或成员编号不一致时不改按同名替代。源照片已被主动移除时不能凭空恢复，需重新选图或恢复备份。
- 食谱管理通过选中卡片后底部「隐藏选中」「删除自建」统一操作，卡片右下角不再重复显示隐藏/删除按钮。隐藏列表增加管理、多选、全选、批量恢复/删除；混选预设时删除计数只包含自建，预设保留。
- 完整删除移除当前菜谱库中的名称、配料、照片和隐藏标记，保留全部日期计划/记录、营养小计、资料、自定义食材、分量记忆；旧计划继续可操作，图像回退默认。删除不能直接撤销，已有备份仍可能包含菜谱且可恢复。恢复隐藏及撤销最近隐藏不能复活已完整删除的菜谱。
- 删除确认取消不变；确认期间数据已变化则阻止；持久化失败不更新内存或清勾选。旧编辑草稿不能把删除的源菜谱重新保存成同ID。主存储版本及备份封装不升级，旧无编号数据仍有效。

### 3.5 自定义食材

- 入口为记录页“＋添加”中的“＋添加新食材”，已吃和计划模式均可使用；无搜索结果时可从搜索词继续新增。
- 必填名称、已知分量、对应热量和分类；热量支持千卡/千焦。已知克数须大于0且不超过5000克，允许0热量；名称去除首尾空白后1–50字。
- 示例：150克对应180千卡，换算为120千卡/100克；实际添加75克应计90千卡。753.12千焦/150克得出同样结果。
- 分类为主食、蛋白质、蔬菜、水果、油脂、其他。依据有限名称规则建议，不根据热量推断营养类型；混合或不确定的食品归其他，允许手选。
- 保存后提供参考分量快捷项和实际克数输入；快捷项不是建议摄入量。分类与热量换算不等于自动决定用户该吃多少。
- 蛋白质、碳水、脂肪按输入参考分量填写，选填；校验非负、单项及合计与分量关系。超过合理热量上限提示核对单位。
- 重复名称提示用品牌或做法区分；保存失败不更新内存状态，退出未保存内容先确认。
- 新食材共享给搜索、记录、计划、自建菜谱及同类配料替换，刷新后仍可使用。

### 3.6 替换确认、双类别管理与提示（R10）

- 点击替换候选只选中，不写入；精确克数变动同步预览原/新食材热量与菜谱合计，复用既有分量与营养计算。未选同类候选、克数不大于0或超过5000均不能确认；取消/关闭不修改源。
- 预设确认另存一份我的搭配，自建确认更新原ID及保留照片；旧计划/已吃文字、克数和营养快照不追溯修改，图片按R9关联规则跟随当前源。保存失败保留候选/克数可重试，成功后同一替换会话不能再次写入；数据已变化阻止过时会话覆盖或复活已删菜谱。
- 食谱管理内部“隐藏食谱（数量）／现有食谱（数量）”切换，每次一个列表滚动；顶部分页/空间与底部操作固定。现有是未隐藏菜谱，不两边重复；切换清勾选并退出批量管理，避免跨类操作。
- 普通入口默认隐藏；现有可筛选“只看有自选照片”，直接仅移除照片，不新增重复删除卡片。超限入口优先现有带照；只有隐藏项占空间则定位隐藏列表。内置图不占自选照片配额。
- 清理前说明文字/配料、隐藏状态及计划/已吃数值保留，关联计划图回默认，照片不能直接撤销，外部备份不会擦除；取消/失败不报释放成功。已用/可用空间来自当前已保存数据，仍按编码长度统计。
- 清理上层面板关闭后保留原编辑名称、餐次、食材及克数和新选照片；成功释放后解除已解决的超限提示，保存/刷新一致。列表空、没有自选照片、长菜名均可达主要入口。
- 尚有待吃显示真实“2 项待吃 · 吃过再确认”；有计划且待吃0显示“今天的计划已全部确认”，历史使用“当日”。无计划沿用空状态；记已吃、撤回、批量等操作和计划/摄入口径保持。
- 本轮明确不调整食材生熟/干重状态、重量、快捷份量和营养库数值；相关口径建议留下一轮独立核查，不把所有米面改成干重。

### 3.7 现有食谱管理与已吃菜份（R11）

- 现有/隐藏各自管理，列表互斥。现有自建明确编辑入口，复用名称、餐次、配料/克数和照片表单；内置原位查看配料或另存新ID，不修改内置定义。批量隐藏含内置/自建，完整删除只计自建；切分类/照片筛选清选择，确认取消或失败保持原数据。
- 超限原草稿保持挂载；管理中另一份编辑/另存有独立副本。第二份清理返回第二份，退出其编辑再回原草稿；不能覆盖名称、餐次、配料、精确克数和新照片，不能同时开启第三份编辑。
- 已吃菜卡顶部为当时菜名和实际合计，3条配料默认全显示，超过4条默认3条并可展开全部。每项仍有实际克数/热量/修改；缺图回退不阻止记录，未知营养继续“未完善”。
- 标签、列表标题与管理统一按展示项计数，一份菜1项，单食物1项；确认明确选中项数、实际明细条数及扣除摄入。底层entries仍逐食材保存，删除/撤销沿用精确计划关联。
- 份次来自每次加入的grp编号，不能按菜名、recipeId或时间合并。同菜两次分别显示；部分已吃只累计真实记录，补记剩余归原份。历史小计不因展示分组重算。
- 可选dish标签仅存份次、当时名称、可选源编号；不复制照片。源改名/改配料/隐藏/删除或计划移除后，已有摄入的菜名、克数、营养值保留；图片仍读取当前源，删除源后回默认。
- 旧记录只有可靠现存计划关联才只读分组；来源/名称冲突、重复关联或无计划的孤立旧记录独立显示。明确移除计划等操作前捕获可靠标签，不批量重写真实历史。
- v2/v3备份及journal-v2不升级；合并同一天同一菜份冲突整份保留本机，不从备份补入同份的另一些配料或复活计划。独立份次/食物仍可追加，完整恢复保留原备份内容；界面说明冲突策略。

## 4. 计算和数据保护要求

- 每100克千卡 = 输入千卡 ÷ 输入克数 ×100；千焦先除以4.184。统一用分量计算，汇总后展示取整。
- 沿用原有基础代谢、活动系数及体重分档缺口估算。根据用户授权的口径核查，取消原周期固定加50千卡及周期专属营养比例，统一碳水48%、蛋白质28%、脂肪24%；周期仅保留一般饮食提示。依据与边界见[第二轮交接](../ROUND2-HANDOFF.md)。
- 原食材库数据不随美化改写，不强行让标签热量等于宏量按4/4/9折算值。这是饮食工具估算，不能描述为医学个体化处方。
- 某营养项含未知值时，该项汇总显示“未完善”；其他完整项照常显示。营养不完整时暂停按营养差额推荐，避免把缺失误当不足。
- 主存储键仍为 `journal-v2`，统一保存按日记录、计划、目标、资料、起始日、菜谱、偏好和可选自定义食材；先持久化成功，再更新页面状态。
- 读取并兼容旧数据，保留旧键与历史小计；用户主动修改记录分量时才重算。没有备份且已被旧版覆盖的历史无法恢复。
- 导出包含自定义食材时使用v3备份封装，无自定义食材时为v2；本版可读v2/v3。存储主键版本与导出封装版本是不同概念。
- 导入先校验并预览，默认合并、本机冲突优先；完整恢复前保留一份导入前副本。存在后续修改时不能用直接撤销覆盖新数据。
- 自定义食材数字编号冲突时自动重编号并同步关联；同独立标识但内容不同则拒绝合并，防止混用。
- 本地存储不提供跨设备自动同步；清缓存或换设备前应保存外部备份。迁移、主存储或副本写入失败均应提示并保留原数据。
- 菜谱新增可选 `photo`，仅接受自包含JPEG/PNG Base64，不以网络URL、blob或微信临时路径作为持久照片。压缩最长边≤480px、单张≤36KiB，全部照片编码总长≤512KiB，隐藏菜谱也计入；超限/写入失败不替换原主数据。微信显示文件可由主数据重新生成。
- 照片随原有v2/v3备份保存，无照片旧菜谱继续可用；照片不参与热量/营养推断。照片备份恢复已在独立H5测试数据上完成，用户真实微信旧数据升级仍未验证。

### 4.1 视觉与交互边界

- 预设食物图尽量对应实际配料，统一比例；替换后不匹配的菜谱使用默认图，不用视频截图充当素材，不在图片里烘焙按钮、数字或正文。
- 选中、加入成功、配料展开、确认已吃、修改分量均有可感知状态，触摸端不依赖悬停，不故意延迟保存或播放虚假加载进度。
- 没有目标时不虚构百分比，未知营养保留“未完善”，未填身体资料仍能记录；不为填满页面增加无数据来源统计、计时器或视频播放。
